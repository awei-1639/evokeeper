# EvoKeeper 项目计划书
## 自进化开源社区助手（Self-Evolving Community Agent）

> 版本 v1.0 · 2026-09-13 · 作者：邱伟洪
> 定位：8-10 周可完成的个人项目，同时是全栈 Agent 开发的学习载体、求职作品与潜在商业产品的种子。
> 一句话：一个挂在开源仓库上的维护者助手 Bot——自动分诊 issue、回答技术问题，并且每次答错都会被记录、离线归纳为经验、通过评测门禁后以新版本上线，从而"越用越准"，全程可审计、可回滚。

---

## 1. 第一性原理推演

不基于类比（"别人做了 bot 所以我也做 bot"），只基于以下事实公理推导：

| # | 公理（可验证的事实） | 来源 |
|---|---|---|
| A1 | LLM 权重在两次模型发布之间是冻结的，它不会从自己的运行错误中改变行为 | 模型部署的基本事实 |
| A2 | Agent 的失败不是均匀随机的，而是聚类的：少数失败模式贡献了大部分错误 | AWM、EvoSkill 等 2025-2026 研究的共同结论 |
| A3 | Agent 行为不只由权重决定：System Prompt / Skill / MCP / Tools / Memory 都是可写状态，改动它们即改变行为，且无需训练 | MetaRSI 对 Harness 层的定义 |
| A4 | 对可写状态的改动可能变好也可能变坏；只有存在验证器时，改进才可判定 | MetaRSI 定律 1：验证器决定自我改进的边界 |
| A5 | 经验放在 Harness 层有持续的推理成本，内化进模型是一次性成本，但训练不可得（成本/能力约束） | MetaRSI 定律 3（能力载体与成本） |

**推演链条：**

1. 由 A1+A2：一个长期运行的 Agent，其价值增量不在"初始能力"，而在**经验积累速率 × 经验留存质量**。
2. 由 A3：经验积累不必训练模型——把经验写进 Harness 层即可。
3. 由 A4：裸写不安全，必须让每次经验变更**经过验证器裁决**，并像代码一样**版本化、可回滚**。
4. 工程结论：把"经验积累"做成一套类似 CI/CD 的系统流程——**经验 CI/CD**：轨迹沉淀 → 离线整理 → 候选经验生成 → 评测门禁 → 灰度发布。这就是项目本体。
5. 由 A4 + 场景筛选四条件（任务可验证、轨迹自动产生、失败有模式可归纳、用户触达成本≈0）→ 选定**开源社区 issue 分诊/技术问答**为首发场景：issue 关闭/重开/维护者纠正是天然验证器，历史 issue 是现成训练语料，GitHub 公开免费。
6. 由 A5 + 资源约束：MVP 阶段能力全部放在 Harness 层（不训练模型）；这同时是对 MetaRSI 范式"在真实业务域"的工程化验证（原论文只验证了代码/数学基准）。

**从公理直接推出的三条设计红线（先于一切功能）：**
- R1 没有评测门禁的进化 = 随机漂移，禁止任何经验直接生效；
- R2 Agent 对仓库只有最小写权限（评论/打标签），禁止改代码、禁止发 PR（MVP 阶段验证器不够强）；
- R3 每一次行为必须留痕（轨迹 + 成本 + 版本），否则无法归因、无法回滚。

## 2. 项目定义

### 2.1 目标

| 层次 | 目标 | 衡量标准 |
|---|---|---|
| 产品 | 开源维护者的分诊/问答负担下降 | 分诊准确率、issue 首响时间 |
| 技术 | 跑通"经验 CI/CD"完整闭环 ≥ 8 个版本迭代 | 有版本曲线：成功率随版本上升 |
| 学习 | 掌握 TS 全栈 + Agent 工程化 | 管理台独立交付、核心引擎模块化 |
| 求职 | 成为可深度追问的头部项目 | GitHub 开源 + 数据化 README |

### 2.2 北极星指标与护栏指标

- **北极星**：分诊准确率（对比维护者最终标签）与独立解答率随版本的**上升斜率**。
- **护栏**：单次处理 token 成本不升高超 10%；holdout 集任一切片回退 < 1pt；误答率（错误但自信的回答）；回滚次数。

### 2.3 非目标（MVP 冻结清单，防范围失控）

- ❌ 不自动修改代码、不发 PR（验证器不够强，风险不对称）
- ❌ 不做多租户 SaaS（先单实例服务 2-5 个仓库）
- ❌ 不做模型训练/微调（A5）
- ❌ 不做实时语音、移动端
- ✅ 只做：分诊（打标签）、技术问答（评论回复）、不确定时求助转人工

## 5. 核心设计

### 5.1 轨迹与失败判别

每条轨迹记录：issue 上下文、Agent 各步骤（含 prompt 版本号）、工具调用、输出、**反应信号**、成本。

失败信号分级（防"判错=进化方向错误"）：
- 显式失败：维护者改标签 / 重开 issue / 评论纠正 / 用户明显不满；
- 隐式失败：用户追问 ≥2 次且未采纳建议后弃用；
- **unclear（无反应）：默认不进整理管线**，只进周报"低信号池"供人工抽样（依据 Reflexion——噪声反思比没有反思更糟；无反应 ≠ 失败也不 ≈ 成功）；判别规则表与窗口见 `docs/design.md` §5；
- 每周人工抽检 20 条校准判别规则（判别器本身也要评测）；抽检一致率 < 0.8 则递增 `judgeRuleVersion` 修订规则，禁止原地改。

### 5.2 记忆分层（对应论文：Mem0 / A-MEM / MemoryOS）

| 类型 | 内容 | 生命周期 |
|---|---|---|
| 情景 | 单次处理经历（摘要） | 随失败判别进入整理管线 |
| 语义 | 仓库事实："该项目 X 功能在 v2 已废弃" | 带来源与时效，可失效 |
| 技能（程序性） | "遇到 EOF 构建报错先查缓存损坏" | 独立 .md 技能文件，版本化 |
| 偏好 | 维护者风格："标签只用 bug/feature" | 按仓库隔离 |

写入遵循最小上下文：工具只返回业务结果，过程数据不进提示词（实习经验的直接迁移）。

### 5.3 睡眠整理（LightMem / AWM 思路）

每周定时：新轨迹 → 失败轨迹聚类（embedding + 规则）→ LLM 归纳模式 → 生成候选经验（类型 + 内容 + 证据链轨迹 ID + 预期影响切片）→ 进入评测队列。成功模式同样归纳（放大正向能力）。整理发生在任务之后而非执行中，生产环境零风险。

### 5.4 评测体系与门禁规则（项目灵魂）

**数据集**：从目标仓库历史 issue 构建 200-300 条 golden set（分诊标签 + 问答对，标注规范留档），dev:holdout = 8:2，holdout 只读。另备 30 条对抗样本（含 issue 内容注入攻击，W8 用）。

**指标**：分诊 Accuracy / 宏 F1；回答质量 = LLM-as-judge（rubric 5 维：正确性/完整性/可操作性/语气/引用）+ 每周人工抽检 20 条校准 judge；独立解答率（人工确认）；P50/P95 延迟；token 成本/次。

**门禁规则（全部满足才可发布）**：
1. dev 集总体指标提升 ≥ 2pt（bootstrap 95% 置信区间下界 > 0）；
2. holdout 任一切片回退 < 1pt；
3. 对抗样本不恶化；
4. 成本不升高超 10%；
5. 新版本先在历史轨迹上**回放**（影子评估）通过。

### 5.5 版本化与灰度发布

经验/prompt/技能均为带版本号的实体，发布 = 生成 diff → 灰度（先 1 个仓库或 20% 流量）观察 48h 指标 → 全量；任何时刻一键回滚。每周自动生成《进化周报》：本周归纳了什么、上线了什么、数据变化。

### 5.6 MCP 工具治理网关（可独立开源的副产品）

工具调用统一过网关：权限分级（读公开数据/写评论/打标签，各自最小化）、审计日志、限流熔断、幂等键。这是 A 方向（MCP 治理）的落地，也是给进化框架的第二重保护。

### 5.7 安全设计（必须项，非加分项）

- **Prompt Injection**：issue 正文是"数据"不是"指令"——结构化隔离、指令层级声明、输出白名单（只允许 标签枚举/回复文本/转人工 三种动作）；
- **GitHub App 最小权限**：issues:write（评论+标签）+ metadata:read，不申请 code write；
- **幻觉引用护栏**：回复中引用的 issue/文档必须真实存在（检测后抑制，OfferCraft 经验）；
- 参考 CodeRabbit 2025 年 RCE 事件教训：任何外部输入（含 .rubocop.yml 类配置）不进执行路径。

## 6. 十周里程碑

| 周 | 目标 | 交付物 / 验收标准 |
|---|---|---|
| W1 | 理论 + 数据地基 | 论文 5 篇精读完（见 §8）；选定目标仓库；golden set v1 ≥ 150 条（双人标注一致性 κ≥0.75）；monorepo 骨架 + CI |
| W2 | 静态 Agent v1 | 分诊 + RAG 问答跑通，接入自己仓库；基线：分诊准确率、成本记录在案 |
| W3 | 轨迹 + 记忆 + 路由 | 轨迹库全量落库；记忆层 v1；LLM 分级路由与 usage 结算；失败判别规则 v1 |
| W4 | 真实流量 | 2-3 个友好仓库接入；连续 7 天真实运行；基线报告 v1（这是后面一切对比的锚点） |
| W5 | 睡眠整理 v1 | 失败聚类 → 候选经验自动生成 ≥ 10 条（人工评审队列） |
| W6 | **关键里程碑：完整进化循环** | 评测门禁 + 版本化发布上线；**第一个经验正式发布为 v2**；与 v1 基线对比数据完整 |
| W7 | 管理台 v1（TS 学习重点周） | 轨迹查看器、记忆演化时间线、评测报告、一键回滚全部可用 |
| W8 | 安全 + 网关 | 对抗样本评测接入门禁；MCP 网关模块化（权限/审计/限流）；injection 攻击演练报告 |
| W9 | 运营与数据 | 仓库数 ≥ 5 或处理量 ≥ 200 issue；进化周报自动化；运行 ≥ 4 个版本的成长曲线 |
| W10 | 发布与叙事 | 开源发布（README 含架构图、成长曲线、评测方法学）；简历定稿；3 分钟 demo 视频 |

**进度落后时的砍法**（预先决定，避免临场纠结）：先砍 W8 网关模块化（退化为进程内中间件）→ 再砍管理台的灰度控制台（保留查看功能）→ 但 **W6 评测门禁永不砍**（砍了项目就不成立）。

## 7. 风险登记册

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| golden set 质量差 → 门禁形同虚设 | 中 | 致命 | 双人标注 + 一致性系数；每周迭代标注规范；judge 人工校准 |
| 判错当失败 → 进化方向错误 | 中 | 高 | 失败信号分级 + 每周人工抽检校准；候选经验必须附证据链 |
| 小样本噪声导致假提升 | 高 | 中 | bootstrap 置信区间；holdout 只读；多周趋势看斜率 |
| issue 注入攻击 | 高 | 高 | §5.7 指令分层 + 动作白名单 + 对抗评测集 |
| token 成本失控 | 中 | 中 | 分级路由 + 决策缓存 + 周预算告警（见 §9） |
| webhook 丢失/重复 | 中 | 低 | 队列至少一次投递 + Inbox 幂等（TradeHub 模式迁移） |
| 范围失控 | 高 | 高 | §2.3 冻结清单 + §6 砍单顺序 |
| 动力衰减（8 周以上长跑） | 中 | 高 | 周报公开（GitHub Discussions）；每两周一次可展示的中间成果 |

**简历条目（示例，数据以实际运行为准）：**

> **EvoKeeper · 自进化开源社区助手（个人项目，开源）**
> 参考 MetaRSI 的 Loop Kernel 范式，实现"经验 CI/CD"闭环（轨迹沉淀→睡眠式整理→评测门禁→版本化灰度发布），使 issue 分诊准确率在 X 周内从 71% 提升至 91%（golden set N=250，95% CI）；记忆层四类分层 + MCP 工具治理网关（权限分级/审计/限流）；Next.js 管理台含轨迹查看器与回滚控制台；运营 X 个仓库、处理 N 个 issue，单次成本 ¥0.0X。

**面试故事线（STAR）**：
- S/T：静态 Agent 因重复犯错被弃用（引用行业数据与 CodeRabbit 的 Learnings 动机）；
- A：把经验积累工程化为带评测门禁的发布流程；遇到的最大难点是"判错会被当成失败经验"→ 设计失败信号分级 + 人工抽检校准判别器；
- R：给出成长曲线 + 一次被门禁拦下的坏经验案例（证明门禁真实工作，这是最加分的细节）。

**预判追问与答案要点**：
- 为什么不用 RL/微调？→ MetaRSI 定律 3：Harness 层成本结构更适合当前阶段；数据量不足；
- LLM-judge 不可靠怎么办？→ 人工抽检校准 + 置信区间 + 多周趋势；
- 被注入攻击怎么办？→ 指令分层 + 动作白名单 + 对抗集进门禁；
- 和 CodeRabbit 什么关系？→ 它验证了品类，其进化停留在偏好记忆；本项目的贡献是系统性经验发布流程且开源可自部署。

## 11. 商业叙事与后续路线

1. **验证期（本项目）**：免费服务开源社区，积累使用量与成长数据；
2. **开源 core + 托管**：私有仓库托管收费（对标 CodeRabbit 的企业版策略，开源可自部署是差异点）；
3. **场景迁移**：同一引擎切企业内部 IT 服务台/工单（真正付费场景），验证"框架场景无关"的设计承诺；
4. 面试叙事：从开源场景验证 → 迁移企业场景，完整对应"产品从 0 到 1"的能力模型。

## 12. 术语表

- **Harness**：模型权重之外、决定 Agent 行为的可写层（prompt/技能/工具/记忆）；**Loop Kernel**：反馈→学习信号→改动→验证→回流的统一闭环；**golden set**：人工标注的标准评测集；**holdout**：只读留存集，防过拟合评测集；**影子评估**：新版本在历史轨迹上离线回放。
